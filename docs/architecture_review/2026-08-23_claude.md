# Loco — architecture & product review

**Date:** 2026-08-23
**Reviewer:** Claude (Opus 5)
**Scope:** Full repo at commit `1951ce3`. Read ~8.2k lines of Rust, all docs, schema types, Hurl suites, and both frontends.
**Baseline state:** `cargo test --workspace` → 113 passing, 0 failing. `cargo clippy --workspace` → clean.

---

## First, what's genuinely good

This is not a typical unfinished side project. Several things are better than they need to be:

- **`docs/identity.md` is excellent.** The person/site-user split, the argument for why grants live on permission sets rather than collections, the explicit non-goals list — that's a document most funded startups don't write. The reasoning ("a managed package can't carry the installer's access policy") is correct and non-obvious.
- **`pathTemplate` as the single source of truth** for identity, storage location, and variable extraction is an elegant core. `from_path`/`to_path` roundtrip cleanly, and enforcing that template vars be `slug` + `createOnly` at parse time is the right kind of strictness.
- **The scope-extractor pattern** (`SiteScope`, `VersionScope`, `CollectionScope`) is idiomatic Axum and keeps authz out of handlers. `VersionSchema` and `ProjectConfig` as scoped views over the global store are the right abstraction — handlers never touch `SchemaStore` directly.
- **Test discipline is real.** Hurl suites as executable spec, unit tests for pure logic, fixtures per suite. The `authz.rs` permission-set tests are thorough.

So the critique below is against a high bar.

---

## Critical: broken access control on `/auth/users`

**`loco-apps/src/handlers/auth.rs:70-121`** — `create_user`, `list_users`, `update_user`, and `delete_user` take `_user: AuthenticatedUser` and **discard it**. Any authenticated identity can delete or rename any other identity by id:

```
DELETE /auth/users/{any-id}   Authorization: Bearer <any valid token>
```

`delete_user` also calls `revoke_all_sessions`. So the lowest-privilege editor on any project can lock out every other user, including org owners. The identity stack (PRs 1–5) rebuilt `/data`, `/schema`, and `/config` around membership and left this route family behind entirely. There is no Hurl coverage for it, which is why it survived.

This is the one thing to fix before anything else.

## Critical: the auth adapter is a prototype wearing production clothes

- **Passwords are plaintext** (`auth/local.rs:28`, comment says so; `password_ok` at `:378` is `provided == Some(stored)`).
- **`StoredApiKey.key_hash` stores the raw key** (`local.rs:633`: `key_hash: key.clone()`). The field name asserts a security property the code does not have. `FUTURE_IDEAS.md` even says "verify this is true of the local adapter" — it isn't.
- **Sessions never expire.** `AuthError::SessionExpired` is constructed nowhere; `validate_session` (`:497`) does a bare map lookup. Every login writes a permanent JSON file that is loaded into a `HashMap` at boot forever. Unbounded growth in both disk and memory.
- **Login is open registration.** `login` → `auto_create_person` (`:382`) creates an account + identity for any unknown handle with any password. Combined with "implicit developer when the identity owns the person account," anyone can `POST /auth/login {"username":"acme","password":"x"}` and instantly hold developer rights over the entire `acme/*` namespace. That is namespace squatting as a feature. It exists to keep Hurl suites simple — but it is unconditional, with no flag to disable it.
- No login rate limiting, no lockout.

None of this is wrong for a local dev adapter. The problem is that `LocalAuthAdapter` is the *only* adapter, it is the default, and nothing in the code marks it as unsafe for real use. At minimum: gate `auto_create_person` behind an env var, rename `key_hash` to `key` until it is one, and add session TTL.

## Architecture

### 1. The dependency/packaging story is half-built — and the untested half is the differentiator

This is the most important architectural finding.

`VersionSchema` resolves collections across self + direct deps. Permission sets deliberately support granting a dep-owned collection (`collection_grant_matches` handles bare and `{project}.{name}` qualified forms). `docs/identity.md` explicitly sells this: *"a consuming project can grant `contacts` even when that collection is owned by a package."*

But the data plane cannot reach dep collections at all. `SiteScope::require_collection` → `validate_collection` (`http/authz.rs:84`) does:

```rust
schema.collections().list(&format!("{user}/{project}/"))
```

That is a prefix scan on the **site's own project** against the **global store**. A collection owned by `loco/core` will never match, so `/data/contacts/list` 404s on a site that depends on it. The permission-set machinery for package collections is currently unreachable.

The same line has a second bug in the opposite direction: the prefix `{user}/{project}/` matches **every version** of the project. A site pinned to published `0.0.1` can read `/data/foo/list` for a collection that exists only in draft `0.0.2-dev`. Version pinning is bypassed for existence checks while field validation (which uses the pinned `VersionSchema`) is not — so writes fail with confusing "unknown field" errors while reads succeed. If a permission set grants `foo`, that is a public read of an unpinned collection.

The fix is the same for both: `require_collection` should go through `self.schema` (the `VersionSchema`), not the global store.

**Test gap that let this through:** `schema_introspect/dependency_inheritance.hurl` claims in its comments to prove "self + transitive deps," but the fixture declares `acme/sales → [acme/crm, base/core]` — both **direct**. The test cannot distinguish direct from transitive, so the core documented invariant ("direct only, not transitive") is unverified. Flip `direct_dependencies` to recurse and every test still passes. And no Hurl suite exercises `/data` against a dep-owned collection at all.

### 2. Cascade deletes miss fieldsets — with evidence in the repo

`VersionSchema::delete_collection` cascades fields *and* fieldsets. But `ProjectConfig::delete_project` (`project_config.rs:91`) and `delete_version` (`:205`) cascade fields, collections, permission_sets, and manifests — **not fieldsets**.

The damage is visible in git: `loco-apps/schemas/instances/ben/pr2check/versions/0.0.1-dev/fieldsets/note/default.yaml` is committed and is the *only* file under `ben/pr2check` — an orphan left behind when that project was deleted. Because instance keys are paths, recreating `ben/pr2check` would silently inherit that stale fieldset.

Related: `.gitignore` intends `ben/…` to be scratch via `/loco-apps/schemas/instances/*` + `!…/loco/`, but `ben/pets` and `ben/pr2check` were committed before that rule and remain tracked — gitignore does not apply to tracked files.

### 3. Boot is O(files × types), and everything is in memory

Generated `SchemaStore::load` creates a `YamlFsAdapter` per type, each pointed at the **whole** instances directory, and each does a full recursive walk calling `read_to_string` on every `.yaml` file. With 8 types, every file on disk is read from disk 8 times and discarded 7 times (`from_path` returns `None`).

That is fine at 31 files. It is a hard ceiling for the hosted platform in `FUTURE_IDEAS.md`: boot cost scales with *total tenants × type count*, and the entire multi-tenant schema universe must fit in RAM before serving the first request. There is no lazy or per-project loading.

Cheap fix now, expensive later: walk the tree **once**, try each type's `from_path` against each key, dispatch. That alone is an 8× boot improvement and changes no interface.

### 4. Durability: a single bad YAML file bricks the server

`YamlFsAdapter::write` does `fs::write` directly — no temp-file + atomic rename. A crash or a full disk mid-write leaves a truncated file. On next boot, `load_all` propagates the parse error up through `SchemaStore::load`, which `server.rs:57` handles with `.expect("failed to load schema")`. **One corrupt file anywhere in the tree means the server will not start**, for any tenant.

Two independent fixes: write to `{path}.tmp` then `rename` (atomic on POSIX), and make `load_all` skip-and-log malformed files rather than failing the whole load.

### 5. No transactions, and read-modify-write races

- `InstanceStore::create` (`store.rs:76`) checks `contains_key` under a read lock, drops it, then writes — classic TOCTOU. Two concurrent creates can both pass the check.
- `append_to_auto_add_sets` / `remove_from_all_fieldsets` are read-clone-modify-write on the fieldset list with no locking across the sequence. Two concurrent `create_field` calls lose one field from the ordering.
- Multi-step operations (create collection + default fieldset; delete project + purge datasets) have no atomicity. The code acknowledges this ("best-effort cascade," "failures here are intentionally non-fatal"), and the read path tolerating dangling names is a good defensive choice — but "eventually inconsistent metadata store" is a load-bearing decision that should be deliberate, not emergent.

This is the deepest tension in the design: **YAML-files-on-disk for schema, SQLite for data.** Two storage engines, two consistency models, and the one holding the most structurally-important data (schema) is the one with no transactions, no atomic writes, and no concurrency control. Worth deciding now whether the YAML tree is the source of truth (git-friendly, diffable, human-editable — real benefits) or just the *export format* over a transactional store.

## Product / data model gaps

### 6. `list` returns everything — no query layer

`DataAdapter::list(dataset_id, collection)` has no filter, sort, pagination, or projection, and every caller loads all matching records into memory and JSON-serializes them. Studio's record table does this. So does the public demo page.

For an "Airtable/Salesforce for agents," this is the single biggest functional gap. Every realistic use — an agent asking "open deals over $10k, newest first" — is impossible. It also most constrains later design: adding filter/sort/paginate to `DataAdapter` after multiple adapters and SDKs exist is much harder than now, when there are two adapters and no clients.

### 7. `Value` is scalar-only

`loco-lake/src/value.rs` has String/Integer/Float/Boolean/Null. No array, no object. So:

- The `list` field type — supported in *type definitions*, parsed, codegen'd — **cannot be stored on a record**. The roadmap's "stop offering `list` as a record field type" concedes this.
- Every future field type in the roadmap (reference, multi-select, file, rich text) needs a non-scalar `Value` or a stringly-typed encoding.

Since `Value` is `#[serde(untagged)]` and already stored as a JSON blob in SQLite, adding `Array(Vec<Value>)` and `Object(Map<String, Value>)` is nearly free *today* and gets much more expensive once records exist in the wild.

### 8. Versioning is half a feature

You can create versions, mark drafts by the `-` convention, and pin sites to them. You cannot:

- **Publish** — no copy-draft-to-release operation. Making `0.0.1` from `0.0.1-dev` means recreating every collection/field/fieldset by hand.
- **Diff** two versions.
- **Migrate** — records are keyed `(dataset_id, collection, id)` with no version dimension. Repointing a site from `0.0.1` to `0.0.2` silently reinterprets existing data under a new schema. Read-time diagnostics surface the drift as warnings, which is a decent safety net, but there is no migration or backfill path.

Also, `is_draft_version` = `version.contains('-')` (`authz.rs`). That means `0.0.1-dev` is a draft and so is `my-app`. Using a substring check on a free-form slug as the sole gate for schema mutability is fragile for something this security-relevant. A `draft: bool` on the manifest would be unambiguous and costs no type change.

### 9. Positioning vs. where the effort went

`ROADMAP.md` says: *"Backend-first… Studio is a convenient editor, not the interface the platform is built around,"* and the product is *"aimed at AI agents and tools."*

But Studio is ~2,300 lines of the most-iterated code in the repo (dark mode, logo, GitHub-styling commits), and the agent interface — MCP, CLI, `@loco/client` — is 0 lines. The stated primary interface does not exist; the stated secondary one is the most polished thing here. That is a real misallocation, and worth naming honestly.

A gentle push back on **"Studio is itself a Loco site."** It is conceptually cute and costs `loco/studio` and `loco/cards` projects, a `studio` dataset, and site headers on requests that have nothing to do with a site. It pays off only if Studio's own config is actually user-editable through Loco. Right now it is overhead. `loco/cards` in particular looks vestigial — a project and site with an empty manifest and no collections, still referenced by Hurl fixtures as a header value.

## Where to go next

Honest read: **the roadmap's #1 (finish the schema→form loop) is the wrong next thing.** It is Studio polish — improving the surface the roadmap says is not the product — and it is the easy, satisfying work. Meanwhile the two things that would actually validate the thesis are untouched.

### Phase 0 — stop the bleeding (a day or two)

1. Gate `/auth/users/*` on membership/self, with Hurl coverage. This is a live hole.
2. Session TTL + expiry sweep; env-gate `auto_create_person`; rename `key_hash` or actually hash it.
3. Fix `require_collection` to use `VersionSchema` — closes both the version-pin bypass *and* unblocks dep collections on `/data`.
4. Add fieldsets to the two cascade paths; delete the `ben/pr2check` orphan and `git rm --cached` the tracked `ben/` trees.
5. Atomic YAML writes (temp + rename) and skip-don't-die on malformed instance files.

### Phase 1 — make the differentiator real (the actual bet)

The unique idea is not "schema-driven backend" — Airtable, Sanity, Directus, Xata, and Baserow all exist. It is **versioned schema as a dependency graph with per-site permission policy**: install `loco/crm@0.0.2` into your project, extend its collections, and choose your own public policy without forking the package. Nobody ships that. `docs/identity.md` already argues for it better than most product specs.

So prove it end to end:

- A Hurl suite where project B depends on package A, stores records in an A-owned collection, and grants public read on it via a permission set — the exact scenario the identity doc describes.
- A `direct`-vs-`transitive` test that would actually fail if the rule changed.
- Version **publish** (copy draft → immutable release) and a schema **diff**. Without publish, dependency pinning is theoretical because nothing can ever be depended on stably.

### Phase 2 — the query layer

Filter/sort/paginate on `DataAdapter`, plus `Array`/`Object` on `Value`. Do this *before* MCP/CLI/SDK, because all three are thin shells over query and every one of them will be reshaped by its signature. Adding it later means breaking three clients instead of zero.

### Phase 3 — then the agent interface

MCP first, not CLI. It is the stated audience, it is a thinner surface than a CLI, and `describe_schema` + `query_records` over a real query layer is a genuinely compelling demo: an agent that discovers your schema and answers questions about your data. That is the thing you can show someone.

**Explicitly defer:** schema→form field metadata, `SelectField` registration, serving `dist/` from Axum. All fine work, none of it de-risks the thesis.

## Smaller notes

- `README.md` / `CLAUDE.md` claim `ben/…` instances are gitignored; two are tracked.
- `AuthError::SessionExpired` is dead code — either implement expiry or drop the variant.
- `Value::Float` in `#[serde(untagged)]` means JSON `3` deserializes as `Integer`. `type_mismatch` correctly accepts `Integer` for a `float` field, but round-tripping a float that happens to be whole silently changes its stored type. Harmless now; will bite on aggregation.
- `require_can_create_under` (`config.rs`) probes org access with the sentinel project id `format!("{account}/_")`. It works, but a synthetic path segment as an authz probe breaks quietly when someone creates a project literally named `_`.
- CORS is `Any`/`Any`/`Any`. Correct and safe given bearer-token-not-cookies (and the reasoning is documented), but worth a config knob before anything is hosted.
- `.playwright-mcp/` has 95 files — gitignored, but worth a periodic sweep.

---

## Bottom line

The foundations are better than the surface suggests, and the thinking in `docs/identity.md` is the most valuable asset in the repo. The risk is not that the architecture is wrong — it is that the polished parts (Studio) and the load-bearing parts (packaging, query, publish) have drifted apart, and the auth layer is a prototype that everything else now depends on. Fix the access-control hole, then spend the next chunk of effort proving the dependency story works end to end. That is the part nobody else has.
