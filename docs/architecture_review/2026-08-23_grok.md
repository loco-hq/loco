# Architecture and product review

**Date:** 2026-08-23
**Author:** Grok

Loco is a coherent prototype of a **headless, versioned schema store plus a schemaless record API**. The identity and request-scope work is unusually good for this stage. The data plane, schema lifecycle, and product loops are not.

The README/roadmap line — “Salesforce or Airtable, but for AI agents” — describes a destination, not what is built. `docs/identity.md` is closer: schema on the server, frontends hold no secrets, `public` is a site principal. Lean into that. Drop the Salesforce comparison until you have relationships, query, and a publish flow.

This review is written while the project is still early enough that direction changes are cheap. Recommendations assume that.

---

## What this actually is

A developer can: log in, create a project (bootstraps `0.0.1-dev` + `dev` dataset + `dev` site), define collections and scalar fields, enter records, and hit REST from curl or a static page.

An agent cannot usefully use it: there is no query, no MCP, no CLI, no SDK, and API keys are unhashed UUIDs sitting in JSON files.

A team cannot use it from Studio: membership and permission sets exist as HTTP (and Hurl) only.

The interesting architectural split is real and worth keeping:

| Layer | What it stores | Persistence |
|---|---|---|
| Platform types (`project`, `collection`, `field`, …) | Compiled at build from YAML | Generated Rust structs |
| User schema instances | Loaded at boot from `schemas/instances/` | YAML files on disk |
| User records | Validated by loco-apps, not the lake | SQLite JSON blobs |
| Identity | Accounts, sessions, membership | JSON files under `loco-apps/auth/` |

User collections are **not** compiled to Rust. The “YAML becomes Rust structs” story is about Loco’s own metadata language. User data is interpreted. That split is correct for a runtime-editable schema. The marketing just pretends they are the same thing.

---

## What is surprisingly solid — keep this

**Request scopes.** `SiteScope` / `VersionScope` / `VersionReadScope` / `CollectionScope` are the best-designed part of the repo. Membership vs site headers vs `public` policy is thought through, documented, and locked in by Hurl (`data_no_auth.hurl`, `schema_read.hurl`, `authorization.hurl`). Most early BaaS projects get this wrong and then cannot add public access later.

**Permission sets on the site, not the collection.** This is a real product decision, not a convenience. Packaged `contacts` should not carry the author’s public-read policy. Additive union, unspecified verbs false, `public` as a principal — all of that is right. Do not collapse it back onto collection flags.

**Loose on load, strict on save** for records. Diagnostics as an open `kind` string (not a closed enum), warnings on read, 400 on write. That will age well when you add required/regex/hooks.

**YAML schema as source of truth.** Git-friendly metadata, `pathTemplate` as the addressing scheme, `${project}` as a 2-segment slug — this is the intellectual core. A future `git://` schema source is a natural extension of what you already built, not a rewrite.

**`VersionSchema` as a request-scoped view** (self + direct deps, snapshot at construction, writes only on drafts). Handlers staying off the global `SchemaStore` is the right anti-leakage pattern. Direct-only deps are a deliberate, defensible choice: visibility is explicit. Keep it until you have an actual package installer.

**Hurl as the product contract.** Auth, public policy, validation, lifecycle, and dependency inheritance are specified. That is better than most prototypes.

Do not rip out codegen, YAML instances, or the site/dataset/version model. Those are the project.

## Architecture: what to change

### 1. The type system does not close

Three type systems that do not agree:

- **Codegen `FieldType`:** string, integer, float, boolean, slug, list, object
- **Collection `field.yaml`:** a free string (`type: list` is allowed)
- **`loco_lake::Value`:** string, integer, float, boolean, null — **no arrays, no objects**

Studio offers `list` as a field type. The validator lets unknown declared types through. The lake cannot store a list. loco-ui renders “Unknown field type”. That is a lie in the product.

Until `Value` grows `Array`/`Object` (or you permanently refuse composite record fields), **stop offering `list`**. Unknown field types should be rejected on schema write, not passed through “for forward compatibility.” Forward compatibility is how you ship a type you cannot round-trip.

`Null` is always valid. There is no `required`. Empty records of undeclared shape can be inserted. Strict-on-save is currently “unknown keys + four scalars.”

### 2. The lake is a KV, not a lake — extend the trait now

`DataAdapter` is:

```
insert / get / update / delete / list / delete_dataset
```

`list` returns every row. Fields live as a JSON text column. SQLite is behind a process-wide `Mutex<Connection>`. `get` maps **all** rusqlite errors to `None`, so a locked or corrupt DB looks like 404. JSON parse failure becomes `{}`.

This is fine for a guestbook. It is not a backend for agents. An agent’s first question after `describe_schema` is “list pets where age > 3.” Today that is “download the collection, filter yourself.”

**Change the trait before you build MCP.** Adding `query { filter, sort, limit, cursor }` later is a breaking change to every adapter and every client. Even v1 as “full scan then filter in process” is enough, as long as the API shape is right. SQLite JSON1 can make that real later without a new abstraction.

Also: collection identity in the lake is `{user}/{project}.{name}` (`paths.rs`) while the dataset is already `{user}/{project}/{dataset}`. The extra prefix is leftover namespacing. Dataset already isolates storage. Use the bare collection name.

### 3. Schema lifecycle is a naming convention, not versioning

Draft = `version.contains('-')`. `1.0.0-rc.1` is writable; `1.0.0` is not. There is **no publish, no clone, no snapshot**. `create_version` writes an empty manifest. To “publish 0.0.1-dev” you recreate every collection, field, fieldset, and permission set by hand.

Without copy-from-version, the version tree is folders with a hyphen convention. Sites pin a version **string** with no existence check. Dataset/site delete does not check references.

This is the highest-leverage backend feature you do not have. A `POST /config/version/...` that copies metadata into a new id (optionally without `-`) makes “draft vs published” true.

### 4. The data plane and the schema view disagree

`SiteScope::require_collection` calls `validate_collection` on the **global** `SchemaStore` with prefix `{user}/{project}/`. That:

1. Accepts a collection from **any version** of the project, not the site’s pin.
2. Rejects collections that exist **only on a direct dependency**, even though `VersionSchema::fields` includes deps and validation uses that view.

So `/data` and `/schema` do not see the same world. Inherited collections in Studio are dead rows for the same reason. The dependency story you already built is unusable for records.

Fix: `scope.schema.collection(name).is_some()`. One lookup, same union as everything else.

Related cascade bugs: `ProjectConfig::delete_project` and `delete_version` delete fields, collections, permission sets, and manifests — **not fieldsets**. `VersionSchema::delete_collection` does cascade fieldsets. Orphans reload on next boot.

### 5. Three persistence worlds that do not transact

YAML schema, JSON auth, SQLite records. Deleting a project tries to purge the lake and swallows lake errors (“metadata is authoritative”). `InstanceStore::create` is check-then-write (TOCTOU). `YamlFsAdapter` is `fs::write`, not atomic rename. `delete_by_prefix` ignores adapter errors then drops cache.

For a single-process local tool this is acceptable. Do not add a second SchemaPersistence impl, git sources, or a hosted multi-instance story on top of it. If you want crash-safety, tempfile + rename in the YAML adapter is a one-file fix.

Auth-as-JSON-files is the one I would plan to replace (SQLite, or the lake itself) before anything leaves localhost. Schema-as-YAML I would keep forever.

### 6. Codegen is justified, but it has dead weight

Eight types is not too few for codegen: `pathTemplate` → `to_path`/`from_path`/`from_yaml` is repetitive and easy to get wrong by hand. Adding `permission_set` as a YAML file is the payoff.

What is not justified:

- `from_map` / `to_map` on every generated type — nothing in loco-apps calls them
- Eight full-tree walks at boot (one `YamlFsAdapter` per type, each walks the whole instances dir)
- Codegen tests that `assert!(code.contains("pub struct Collection"))` instead of compiling the output
- `from_yaml` defaulting missing keys and never rejecting unknown keys — schema instances are looser than records

Do not rewrite codegen. Delete the unused conversion paths, walk the tree once, and compile a fixture in the gen-crate tests.

### 7. Auth is a local-dev toy on the production path

This is the one place to be harsh.

- Passwords stored **plaintext**; compare is `==`
- API keys stored as `key_hash: key` — the field is named hash, the value is the UUID
- Login of an unknown handle **creates an account** (`auto_create_person`) so Hurl does not need fixtures
- Any authenticated user can `list/create/update/delete` all users (`_user` is unused)
- Sessions never expire (`SessionExpired` is dead)
- CORS `*` is correct **only** because you use Bearer, not cookies — keep it that way

`TEST_PASSWORD` and auto-create belong behind `cfg(test)` or an env flag the Hurl runner sets. Hash passwords and keys even in the local adapter. Gate `/auth/users`. The `AuthAdapter` trait is fine; the local impl encodes test conveniences that would be a CVE the day `:3000` is reachable.

## Product: the loops that do not close

Studio is a competent metadata/record admin, not a product. The backend already has capabilities Studio cannot operate.

| Loop | Backend | Studio / example |
|---|---|---|
| Schema + scalar records | Yes | Yes |
| Required / description / variant | No (`field.yaml` is `type` + `label`) | Dispatcher already reads them |
| List fields | Declared, not stored | Offered, then “Unknown field type” |
| Public access policy | Permission sets + site assignment, Hurl-complete | **Invisible.** Site forms omit `public_permission_sets` |
| Team | Org/project membership API | No UI |
| Packages | Manifest deps, direct visibility | Display-only; `updateManifest` never called; inherited collections are dead rows |
| Agents | REST | No MCP, CLI, SDK, or key UI |
| Publish | Hyphen convention | Create empty version |
| Query | `list` everything | Table dump, no filter/sort/page |
| Demo | `loco/demo` guestbook, one string field, public **read** only | `examples/public-page` is a CORS smoke test |

**“Studio is itself a Loco site” is leftover.** `loco/studio` and `loco/cards` have no own collections — they depend on `loco/core.user`, which is **not** wired to login. Auth is `loco-apps/auth/*.json`. The editor is a hardcoded React app. Either dogfood Studio as Loco collections or stop saying it.

**IA:** clicking a project redirects to the first version. Settings is the real project page. Records live under a version URL but data lives on a site (`?site=`). Missing site → a dead form. Two form systems (loco-ui vs raw HTML). Every delete is one click. Collection-delete copy says records will be removed; `delete_collection` only deletes YAML.

**loco-ui** is a small, coherent kit for four scalars + an unregistered `SelectField`. That is the right size. Do not grow it into a design system until the schema can describe more than `type` and `label`. Studio’s `style.css` is a second token set; pick one.

**`FUTURE_IDEAS.md` is stale** in the security section (login still “passes `None`”; metadata-editor allowlist already replaced). Treat ROADMAP + HANDOFF + identity.md as source of truth; prune the parking lot.

## Positioning: change the thesis while it is cheap

Two docs, two products:

- ROADMAP: Salesforce/Airtable for agents
- identity.md: Sanity-shaped; frontends hold no secrets; site users later

You have been building the second. The architecture (YAML schema, sites pin version+dataset, CORS `*`, Bearer, permission sets on the site, Studio as an editor not the runtime) is a **headless structured-data backend**. That is a good product. It is not Salesforce (no relationships, SOQL, FLS, automation) and not Airtable (no grid, views, linked records, field types).

**Recommended thesis:**

> Loco is a versioned, file-backed schema and a site-scoped record API. Humans edit schema in Studio or YAML. Agents and static frontends consume the same HTTP surface. Public policy lives on the site, not the collection.

That gives you a 5-minute demo target: define a collection, pin a public site, curl it, then the same thing from an MCP client. Salesforce language waits for references + query + publish.

Do not build toward a hosted platform, marketplace, scripting engine, or Clerk until that demo is boring.

## Where to go next

Reorder the HANDOFF. Field metadata is real work, but it is not the bottleneck. An agent does not fail because fields lack `description`; it fails because it cannot query, cannot publish a version, and cannot see inherited collections in `/data`.

### Now — make the model true (1–2 weeks)

These are bugs and lies, not features:

1. `/data` collection existence uses `VersionSchema`, not the global store. Bare lake collection names.
2. Cascade fieldsets on project/version delete.
3. Reject unknown field types on schema write. Remove `list` from the picker until `Value` can hold it.
4. Hash passwords and API keys. Stop auto-creating users on login except under a test flag. Gate `/auth/users`.
5. Copy-version (publish/clone) that duplicates collections, fields, fieldsets, permission sets, manifest.

### Then — close two product loops (the actual next)

**A. Headless public app.** Permission-set editor + `public_permission_sets` on the site form. Upgrade `loco/demo` with read+create. Upgrade `examples/public-page` to fetch schema and POST. This is the only loop that currently proves identity.md.

**B. Query + MCP/CLI as one surface.** `GET /data/{collection}/list?…` with filter/sort/limit first (even naive). Then MCP tools and a `loco` CLI on that API: `describe_schema`, CRUD, query. Issue keys from Studio. This is the only loop that proves “for agents.”

Ship A and B against **one real demo** (pets or tasks, 2–3 collections, seed records). Relabel or delete empty `loco/studio` and `loco/cards`.

### Alongside, not instead

ROADMAP #1 still matters, but scope it:

- `description` + `required` on `field.yaml`
- Validate required on create (and on update only if the key is present, or decide that updates cannot clear required fields)
- Drive forms from auto-add fieldset order (tables already do)
- Do **not** add `variant` or register `SelectField` until you have picklist options in the schema

Axum `ServeDir` of `loco-studio/dist` so `cargo run` is the product. Fine as a small PR; not the strategy.

### After the loops close

- Reference field type (this is the jump from guestbook to CRM)
- Picklist
- `@loco/client` extracted from `api.js` (do not redesign it)
- Membership UI (API is done)
- WAL / `spawn_blocking` / don’t map SQLite errors to 404

### Do not do yet

Marketplace, git/npm schema sources, Deno scripting, file lake, Clerk, hosted billing, GraphQL, field-level security, realtime, “Studio as a Loco app.” FUTURE_IDEAS is a gravity well. The risk is adding MCP on a data plane that cannot query, and adding field variants on a type system that cannot store a list.

---

## What not to change

- YAML instances + path templates as the metadata model
- Sites + datasets instead of a tenant registry
- Direct-only dependency visibility (until you have install)
- Permission sets assigned on the site
- Diagnostics as an open set
- Studio as an editor, not the interface the platform is built around
- Hurl as the API spec
- Rust 2021 / Axum / Vite / React — the stack is boring in a good way

The project is early in the right way: the abstractions that would be expensive to unwind (scopes, permission sets, file-backed schema, lake vs metadata) are mostly the ones you should keep. The ones that are wrong (Value vs field types, `validate_collection`, empty versions, plaintext auth, “Salesforce for agents”) are still cheap to fix.

**North star for the next stretch:** a stranger can define a schema, publish a version, assign public read+create, and an agent can query and write it with a key — without opening Studio. Everything that does not serve that can wait.
